## 1. 背景

### 1.1 现状问题（已定位代码根因）

| # | 现象 | 根因 |
|---|---|---|
| P1 | 点「开始自动加载」后**无视数据库已有历史数据，从头全量重下** | `handle_auto_load_action` 无条件调用 `reset_load()` 清零进度；`initial_load` 不检查 `bars_daily` 库存，逐只重复下载 |
| P2 | 「暂停」后**无法继续上次任务** | 暂停仅把 phase 置 `idle`；界面无「继续」入口，唯一入口「开始」又绑死 reset |
| P3 | 库中已有历史数据时，**自动加载完全不工作** | `check_and_start()` 仅在 `bars_daily` 为空时触发；只要有一行数据就直接 `idle`，不感知"缺哪些标的、数据新不新鲜" |
| P4 | 续传定位不可靠 | 游标为位置索引 `current + skipped`，而标的清单每次联网重取（沪深300 + 港股 head(80)），顺序不稳定 → 会跳号/重复 |
| P5 | 失败标的永久丢失 | 异常仅 `skipped += 1`，无重试队列，无失败清单 |
| P6 | 增量更新对港股写错 | `incremental_update()` 对 `.HK` 标的误用 A 股接口 `stock_zh_a_hist`，且 market 误写为 `a_share` |
| P7 | 增量更新覆盖不全（研发评审 D-6 新发现） | `incremental_update()` 每次仅处理 `tickers[:incremental_batch_size]` 且**无游标轮转**——`DISTINCT ticker` 排序后靠后的标的永远轮不到增量更新，长期静默缺数据 |

### 1.2 核心设计转变

V1.2 之前：加载进度以**内存/状态表游标**为准，数据库是被动写入目标。

**V1.3：数据库即事实来源（DB as Source of Truth）。** 任何一次"加载"都不再是"从第 N 只开始下载"，而是：

> 扫描标的清单 → 逐只对比 `bars_daily` 库存（有无数据、最新日期）→ 生成本次**加载计划**（全量 FULL / 增量补缺 GAP / 跳过 SKIP）→ 只执行计划中的缺口部分。

由此，"断点续传""历史数据复用""增量更新"统一为同一套机制：**缺什么补什么，有什么跳什么**。

### 1.3 用户价值

- 标的池约 380 只（沪深300 + 港股约 80），全量加载为分钟级任务；网络抖动、切页、误点、重启应用是常态场景。
- 有历史数据时重复全量下载：浪费带宽、触发 akshare 限频、拖长数据就绪时间、放大被封禁风险。
- 「暂停后可继续」「已有数据不重下」符合用户心智的最低预期，属体验硬伤修复而非锦上添花。

## 2. 目标与非目标

### 2.1 目标

1. 有历史数据的标的**零重复下载**：已新鲜标的直接跳过，不新鲜标的仅补缺口区间。
2. 暂停/中断（含关浏览器、重启应用、进程被杀）后可**一键继续**，从缺口处恢复。
3. 失败标的进入重试队列，主流程结束后自动重试，最终失败清单可见。
4. 「继续」与「重新加载」为两个语义独立的操作，重新加载需二次确认。

### 2.2 非目标（本期不做）

- 不做多数据源容灾（仍以 akshare 为唯一行情源）。
- 不做分钟线/复权数据的缺口补齐（仅日线 `bars_daily`）。
- 不改变标的池构成规则（仍为沪深300成分 + 港股活跃 80 只）。
- 不做加载任务的并发/多线程下载（保持单后台线程 + 限频器）。

## 3. 用户故事

- **US-1**：作为量化研究者，我上周已经加载过全部数据，今天打开系统点「开始加载」，我希望系统只补上周五到今天的缺口，几十秒完成，而不是重下 5 年历史。
- **US-2**：作为用户，我在加载到 180/380 时有事暂停了，明天回来我希望点「继续」，从第 181 只接着跑，而不是从头再来。
- **US-3**：作为用户，加载过程中家里断网导致 12 只标的失败，我希望系统自动重试；实在失败的给我一个清单，我知道缺了谁。
- **US-4**：作为用户，我怀疑某段数据脏了，我希望有一个明确的「重新加载」按钮把数据推倒重来，并且系统会先跟我确认，防止误触。

## 4. 功能需求（EARS 规范）

### FR-1 加载计划生成（历史数据感知）——本 PRD 核心

- **FR-1.1（Event-driven）** When 用户点击「开始加载 / 继续」或系统冷启动触发加载, the system shall 先以**一条聚合 SQL**（`SELECT ticker, COUNT(*), MAX(trade_date) FROM bars_daily GROUP BY ticker`）一次性取回全部标的库存，与标的清单比对后生成加载计划，而非直接下载。〔评审修订 D-1：原文"逐只查询"与风险表 #2 矛盾，统一为单次聚合查询〕
- **FR-1.2（Ubiquitous）** The system shall 按以下规则对每只标的分类：
  - `FULL`：库中无该标的任何日线 → 从 `initial_start` 拉到今天；
  - `GAP`：库中有数据但 `MAX(trade_date) < 最近一个已收盘交易日` → 仅拉 `MAX(trade_date)+1` 至今天；
  - `SKIP`：`MAX(trade_date) ≥ 最近一个已收盘交易日` → 不发起任何网络请求。
- **FR-1.3（Ubiquitous）** The system shall 以"最近一个已收盘交易日"为新鲜度基准（周末/节假日/盘中当日不算缺口），基准计算失败时降级为"最近一个自然日的前一工作日"。
- **FR-1.4（Ubiquitous）** The system shall 在进度统计中把 `SKIP` 计入"已完成"，使进度条反映真实剩余工作量（例：380 只中 300 只已新鲜，则开始即显示 300/380）。
- **FR-1.5（Unwanted）** If 单只标的的库存查询失败, then the system shall 将其按 `FULL` 处理（宁可重下、不可漏下），并记录日志。
- **FR-1.6（Ubiquitous）**〔评审新增 D-2〕 The system shall **按市场区分新鲜度基准**：A 股以 15:00（北京时间）收盘、港股以 16:00（香港时间）收盘为当日已收盘界线，且两市交易日历独立判断（例：香港公众假期 A 股开市时，港股标的不得被误判为 GAP）。P0 允许用"各自工作日近似 + 各自收盘时间"实现，接口需预留交易日历表替换点。
- **FR-1.7（Ubiquitous）**〔评审新增 T-3〕 The system shall 将"当前时间/最近已收盘交易日"的取值封装为**可注入的纯函数**（如 `freshness_baseline(market, now=None)`），使周末/节假日/盘中语义可在任意日期自动化测试，不依赖真实系统时钟。

### FR-2 标的级状态账本（断点续传基础）

- **FR-2.1（Ubiquitous）** The system shall 新增 `symbol_load_state` 表，逐标的记录：`ticker, plan(FULL/GAP/SKIP), status(pending/done/failed), gap_start, rows_loaded, attempts, last_error, updated_at`。
- **FR-2.2（Event-driven）** When 一只标的加载成功写库完成, the system shall 立即将其 `status` 置为 `done`（逐只提交，不整批提交）。
- **FR-2.3（Event-driven）** When 用户点击「继续」, the system shall 仅处理 `status IN (pending, failed)` 的标的，`done` 的标的不重复下载、不重复请求。
- **FR-2.4（Ubiquitous）** The system shall 以标的代码（ticker）而非清单位置索引作为续传定位依据。
- **FR-2.5（Event-driven）** When 一轮加载会话开始（开始/重新加载）, the system shall 将当次标的清单快照写入账本；会话内「继续」复用快照，不重新联网取清单。
- **FR-2.6（Ubiquitous）** The system shall 保证应用重启后账本仍在（落库持久化），「继续」可跨进程生命周期恢复。
- **FR-2.7（Ubiquitous）**〔评审新增 D-3〕 The system shall 在 `symbol_load_state` 中记录 `session_id`；新会话（开始/重新加载）生成计划时**清理不属于当前清单快照的遗留行**（标的池调整后被移出的标的不得残留 pending 状态误导续传）。
- **FR-2.8（Ubiquitous）**〔评审新增 T-4〕 The system shall 保证行情写库**幂等**：同一标的同一区间重复加载不产生重复行、不改变行数（沿用 `bars_daily` 主键 `INSERT OR REPLACE` 语义），验收含幂等断言。
- **FR-2.9（Ubiquitous）**〔评审新增 D-4〕 The system shall 将"单只标的写库 + 账本置 done"放入**同一事务**提交（复用 `DuckDBManager.transaction()`），防止写库成功但账本未更新（或反之）导致续传口径漂移；同时避免逐行 `execute` 的碎片化提交（当前实现为逐行写，需改为单标的批量写）。

### FR-3 操作模型（三态按钮）

- **FR-3.1（State-driven）** While 无进行中会话（首次/上次已完成）, the system shall 仅展示「开始加载」；点击后按 FR-1 生成计划并执行（有历史数据时自然表现为增量补齐）。
- **FR-3.2（State-driven）** While 加载进行中, the system shall 展示「暂停」，并禁用「开始/继续/重新加载」。
- **FR-3.3（Event-driven）** When 用户点击「暂停」, the system shall 在当前标的完成后停止（不截断半只标的的写入），保留账本与进度。
- **FR-3.4（State-driven）** While 处于已暂停状态, the system shall 同时展示「继续」与「重新加载」两个独立按钮。
- **FR-3.5（Event-driven）** When 用户点击「重新加载」, the system shall 弹出二次确认（说明将清空账本并重新核对全部标的）；确认后清空 `symbol_load_state` 与进度，按 FR-1 重新生成计划。注意：重新加载**清空账本，不清空 `bars_daily`**——已有历史数据仍按 FR-1.2 复用（GAP/SKIP），如需彻底重下由「高级选项」提供"忽略库存，全量重下"开关（默认关闭）。
- **FR-3.6（Unwanted）** If 用户在加载中关闭浏览器或应用进程终止, then the system shall 在下次进入页面时识别到未完成会话，展示「继续（上次进行到 N/M）」与「重新加载」。
- **FR-3.7（Ubiquitous）**〔评审新增 D-5：中断识别规则〕 The system shall 采用如下规则识别"遗留 loading 态"：应用启动时若 `phase='loading'` 但本进程内无活动加载线程，则将 phase 修正为 `interrupted`（等价"已暂停"），**不自动恢复下载**，由用户显式点「继续」。禁止依赖心跳超时等复杂机制（单机单进程场景不必要）。
- **FR-3.8（Unwanted）**〔评审新增 T-5：并发防护〕 If 用户快速连点「开始/继续」或在加载线程存活时再次触发, then the system shall 通过互斥锁保证**同一时刻至多一个加载线程**，重复触发直接忽略并保持当前状态；「暂停」通过 `threading.Event` 停止信号实现（当前 `_running` 布尔 + 轮询 phase 存在竞态窗口，需替换）。

### FR-4 失败重试与失败清单

- **FR-4.1（Unwanted）** If 单只标的抓取或写库失败, then the system shall 将其 `status` 置 `failed`、`attempts+1`、记录 `last_error`，并继续处理后续标的（单点失败不中断整体）。
- **FR-4.2（Event-driven）** When 主流程一轮结束且存在 `failed` 标的, the system shall 自动对 `failed` 标的重试，最多 3 轮，轮间退避（默认 5s/15s/60s，**退避序列与轮数须可配置/可注入**〔评审修订 T-6：否则重试用例最长阻塞 80s，CI 不可接受〕）。
- **FR-4.3（State-driven）** While 存在最终失败（3 轮后仍 failed）的标的, the system shall 在页面提供可展开的失败清单（ticker、名称、失败原因、重试次数），并提供「重试失败项」按钮。
- **FR-4.4（Ubiquitous）** The system shall 保证失败重试同样受限频器（RateLimiter）约束。

### FR-5 增量更新修正（随本期一并修复）

- **FR-5.1（Ubiquitous）** The system shall 在定时增量更新中按市场路由接口：A 股走 `stock_zh_a_hist`，港股走 `stock_hk_daily`，且写入的 `market` 字段与标的真实市场一致（修复现存 P6 缺陷）。
- **FR-5.2（Ubiquitous）** The system shall 使定时增量更新复用 FR-1 的计划生成逻辑（GAP/SKIP），与手动加载共用同一套缺口判定，不再维护两套逻辑。
- **FR-5.3（Ubiquitous）**〔评审新增 D-6：修复 P7〕 The system shall 保证定时增量更新**单轮覆盖全部 GAP 标的**（复用 FR-1 计划后天然满足：SKIP 不耗请求、GAP 通常个位数），废弃现有 `tickers[:batch_size]` 无游标截断逻辑；若单轮 GAP 数超过限频预算，则记录续接点，下轮从续接点继续。

### FR-6 状态可视化

- **FR-6.1（Ubiquitous）** The system shall 展示五态：`未开始 / 加载中 / 已暂停 / 已完成 / 部分失败`，并按状态联动按钮可用性（见 §6 交互说明）。
- **FR-6.2（Ubiquitous）** The system shall 在进度区展示：`已完成 X / 总数 M · 复用跳过 S · 增量补齐 G · 失败 F`，让用户直观看到"历史数据帮我省了多少"。
- **FR-6.3（State-driven）** While 计划生成中（扫描库存阶段）, the system shall 展示"正在核对本地数据…"状态，避免用户误以为卡死。
- **FR-6.4（Ubiquitous）**〔评审新增 U-1〕 The system shall 将进度信息**分层展示**：主行仅保留"进度条 + X/M"；`复用 S · 补齐 G · 失败 F` 作为次级小字（`text-muted small`），避免一行四个数字的信息过载；F>0 时失败数用 `text-danger` 且可点击展开清单。
- **FR-6.5（Ubiquitous）**〔评审新增 U-2〕 The system shall 为「继续」「重试失败项」使用**独立组件 id**（`btn-load-resume` / `btn-retry-failed`），不得复用同一按钮换文案（Dash 回调按 id 绑定，复用会导致回调歧义与测试不可寻址）。
- **FR-6.6（Ubiquitous）**〔评审新增 T-7：埋点可断言〕 The system shall 通过标准 `logging`（`logger.info`，结构化 key=value）落地 §8 全部埋点事件，使测试可用 `caplog` 断言，无需额外埋点表。

## 5. 流程说明

### 5.1 主流程（开始/继续）

```
用户点击开始或继续
  → [扫描阶段] 取标的清单（开始=联网取+落快照；继续=读快照）
  → 逐只查 bars_daily 库存 → 写/更新 symbol_load_state（FULL/GAP/SKIP）
  → [执行阶段] 后台线程遍历 status=pending/failed 的标的
       FULL → 拉 initial_start~today → 写库 → done
       GAP  → 拉 gap_start~today   → 写库 → done
       SKIP → 直接 done（计入进度，不联网）
  → [收尾阶段] failed 重试 ≤3 轮 → 仍失败者入失败清单
  → 全部 done → 状态=已完成；有最终失败 → 状态=部分失败
```

### 5.2 暂停/恢复

```
加载中 →「暂停」→ 完成当前标的后线程退出，账本保留 → 已暂停
已暂停 →「继续」→ 跳过 done，从 pending/failed 继续（不联网重取清单）
已暂停 →「重新加载」→ 二次确认 → 清账本（不清 bars_daily）→ 回到主流程
应用重启 → 进页面检测到未完成账本 → 展示「继续（N/M）」
```

### 5.3 与定时任务的关系

每日定时增量更新 = 系统自动触发的一次"开始加载"（FR-5.2 复用同一计划生成），因历史数据在库，天然表现为全 SKIP + 少量 GAP，耗时秒级。

## 6. 交互说明（按钮状态矩阵）

| 状态 | 开始加载 | 暂停 | 继续 | 重新加载 | 状态文案 |
|---|---|---|---|---|---|
| 未开始 | ✅ | — | — | — | 尚未加载数据 |
| 计划生成中 | ⛔ | ⛔ | — | — | 正在核对本地数据… |
| 加载中 | ⛔ | ✅ | ⛔ | ⛔ | 已完成 X/M · 复用 S · 失败 F |
| 已暂停 | — | ⛔ | ✅ | ✅（需确认） | 已暂停，进度 X/M 已保留 |
| 已完成 | — | — | — | ✅（需确认） | 数据已就绪（HH:MM 更新） |
| 部分失败 | — | — | ✅重试失败项 | ✅（需确认） | 完成 X/M，N 只失败（可展开） |

边界交互：
- 「重新加载」确认弹窗文案需明确"不会删除已下载的历史行情，仅重新核对与补齐；如需彻底重下请勾选高级选项"。
- 失败清单行内展示 `代码 名称 · 原因摘要 · 已重试 n 次`，原因做用户可读转译（超时/限频/接口无数据），不暴露堆栈。

设计评审补充（已合入）：
- **U-3 组件清单落地**：二次确认用 `dbc.Modal`（含"彻底重下"`dbc.Checkbox`，默认不勾选、勾选后确认按钮文案变为红色"清空并全量重下"）；失败清单用 `dbc.Collapse` + `dbc.ListGroup`；状态色沿用 Bootstrap 语义色（就绪 `success` / 加载中 `info` / 已暂停 `warning` / 部分失败 `danger`），与 V1.2 搜索三态反馈的用色保持一致。
- **U-4 「继续（N/M）」动态文案**：页面加载即由初始化回调渲染（读取账本聚合），不等用户交互；N/M 取账本 `done/总数`，与进度条同源，禁止两处各算一遍。
- **U-5 失败名称来源**：失败清单中的标的名称从 `symbol_dict` LEFT JOIN 获取（依赖 V1.2），查不到时显示"—"，与缓存表占位规则一致。
- **U-6 「暂停」点击后的过渡态**：因暂停要等当前标的完成（FR-3.3），点击后按钮立即置为不可用并显示"正在暂停…"，防止用户在延迟窗口内重复点击或误以为失效。

## 7. 数据结构

新增表（随 schema 迁移版本 v4 发布）：

```sql
CREATE TABLE IF NOT EXISTS symbol_load_state (
    ticker      VARCHAR PRIMARY KEY,   -- 标准代码，续传定位键
    session_id  VARCHAR NOT NULL,      -- 〔评审修订 D-3〕所属会话，新会话生成计划时清理非当前清单的遗留行
    plan        VARCHAR NOT NULL,      -- FULL / GAP / SKIP
    status      VARCHAR NOT NULL,      -- pending / done / failed
    gap_start   DATE,                  -- GAP 时的补齐起点
    rows_loaded INTEGER DEFAULT 0,
    attempts    INTEGER DEFAULT 0,
    last_error  VARCHAR,
    updated_at  TIMESTAMP
);
```

`auto_load_status` 为现存 KV 表（`key VARCHAR PRIMARY KEY, value VARCHAR`），**结构不变**，仅约定新增 key：`phase / session_id / started_at / plan_full / plan_gap / plan_skip`。〔评审修订 D-7：KV 表扩展无需 ALTER，schema v4 迁移只含 `symbol_load_state` 的 CREATE，走 `store/schema.py` 现有 `_MIGRATIONS` 机制（v3→v4），与 V1.2 `symbol_dict` 同一套迁移路径，迁移可幂等重放〕

废弃 key 清理：v4 迁移时删除旧游标 key（`current/total/skipped` 语义由账本聚合取代，`get_progress()` 改为 `SELECT status, COUNT(*) FROM symbol_load_state GROUP BY status`）。

## 8. 数据指标与埋点

| 指标 | 口径 | 目的 |
|---|---|---|
| 复用率 | SKIP 数 / 总标的数 | 验证历史数据感知价值（预期二次加载 > 90%） |
| 二次加载耗时 | 有历史数据时从点击到完成的耗时 | 目标：从分钟级降到 < 60s |
| 续传成功率 | 「继续」后无重复下载完成的会话占比 | 目标 100% |
| 最终失败率 | 3 轮重试后 failed / 总标的 | 监控数据完整性，目标 < 1% |
| 重新加载点击占比 | 重新加载 / (继续+重新加载) | 若偏高说明用户不信任续传，需回查 |

埋点事件：`load_plan_generated{full,gap,skip}`、`load_paused`、`load_resumed`、`load_reset_confirmed`、`load_symbol_failed{ticker,reason}`、`load_session_done{elapsed_ms,reused}`。

## 9. 验收标准

1. **历史复用**：库中已有 300/380 只标的的最新数据 → 点「开始加载」，网络请求数 ≤ 80 + 少量 GAP 请求；进度条起点即为 300/380；总耗时 < 60s（限频允许下）。
2. **断点续传**：加载到 50/380 时暂停 → 点「继续」，前 50 只不产生任何网络请求，从第 51 只继续。
3. **跨重启续传**：加载中 kill 进程 → 重启应用进入数据中心 → 出现「继续（50/380）」，点击后行为同第 2 条。
4. **新鲜跳过**：当日已完成加载后再次点「开始加载」→ 全部 SKIP，0 个行情下载请求，秒级完成。
5. **缺口补齐**：手工删除某标的最近 10 个交易日数据 → 下次加载该标的被判为 GAP，仅拉取缺失区间，且不重写更早历史。
6. **失败重试**：模拟 5 只标的网络失败 → 主流程后自动重试 ≤3 轮；最终失败清单可见、可一键重试；其余标的正常 done。
7. **重新加载安全**：点「重新加载」必现二次确认；确认后账本清空但 `bars_daily` 行数不减少（未勾选彻底重下时）。
8. **清单快照稳定性**：会话中途沪深300成分调整 → 「继续」仍按快照执行，不跳号不重复；下次「开始加载」才使用新成分。
9. **周末语义**：周六全库最新数据为周五 → 点「开始加载」全部 SKIP（周五即最近已收盘交易日），不误判为缺口。
10. **港股增量正确性**：定时增量后抽查 `.HK` 标的，新增行 `market='hk_connect'` 且价格与 `stock_hk_daily` 一致（P6 修复验证）。〔T：真实网络用例，标记 `network`，不入 CI 门禁〕
11. **连点防抖**〔评审新增 T-5〕：加载中快速连点「开始/继续」5 次 → 全程仅存在一个加载线程，进度单调递增，无重复下载、无异常。
12. **写库幂等**〔评审新增 T-4〕：对同一标的连续执行两次相同区间加载 → `bars_daily` 该标的行数不变，`rows_loaded` 第二次为 0 或等值覆盖，无重复行。
13. **遗留 loading 态恢复**〔评审新增 D-5〕：构造 `phase='loading'` 但无活动线程的库状态 → 启动应用进入页面，状态显示为"已暂停（上次中断）"，不自动开始下载；点「继续」正常续传。
14. **标的池调整清理**〔评审新增 D-3〕：账本中存在已被移出标的池的 ticker（pending 态）→ 新会话「开始加载」后该行被清理，进度分母为新清单数，不出现幽灵 pending。
15. **增量全覆盖**〔评审新增 D-6，P7 修复验证〕：库中 380 只标的全部落后 1 个交易日 → 一次定时增量后 380 只全部补齐（允许分轮续接，但不得存在永远轮不到的标的）。

**验收前提**〔评审新增 T-1〕：第 1/4 条的"< 60s / 秒级"以限频器 `max_per_minute=60`（现网默认）为基准；变更限频配置时按比例折算，验收报告须记录当时配置。第 9 条使用 FR-1.7 的可注入时钟在任意日期执行，不要求真实周末。
