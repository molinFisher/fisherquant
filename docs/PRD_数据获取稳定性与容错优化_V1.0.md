## 1. 背景与问题陈述

「数据查询」Tab 的「开始获取数据」在取**分钟线**时，对多个标的（最多 20 个）串行发起请求。经代码走查，取数路径为：

```
fetch_data（回调，串行循环符号）
  └─ svc.fetch_bars([symbol], ...)
       └─ _retry_fetch(lambda: ak.stock_zh_a_hist_min_em(...))   # 3 次重试，间隔 1.5s
```

而项目**已存在**限流与退避基础设施 `fisher/market/rate_limiter.py`：

- `RateLimiter`（`max_per_minute=20`，令牌桶 + 随机抖动）；
- `retry_with_backoff` 装饰器（指数退避）；
- 全局单例 `get_global_limiter()`。

**但该基础设施在 `fetch_bars` / `_retry_fetch` 中完全未被调用**——每次取数请求都"裸奔"直连数据源，无节流、无限流感知。当一次拉取 20 个分钟线标的时，20+ 次请求在数秒内突发，极易触发东方财富接口的频控，返回 `Max retries exceed`。

| 编号 | 问题                 | 用户感知                              | 根因（代码事实）                                                              | 优先级    |
| -- | ------------------ | --------------------------------- | --------------------------------------------------------------------- | ------ |
| S1 | **多标的取数触发数据源限流**   | 分钟线批量取数大量标的报 `Max retries exceed` | `fetch_bars` 未调用 `RateLimiter.acquire()`，请求无节流；已有的限流器/退避装饰器都没接上       | **P0** |
| S2 | **限流未触发「降速自愈」**    | 一旦被限流，仍按原速重试，越重试越被限               | `_retry_fetch` 固定 1.5s 间隔，不识别 429/限流，也不通知限流器降速                        | **P0** |
| S3 | **失败原因未分类**        | 用户看到"无数据"与"被限流"混在一起，无从判断该重试还是换标的  | `fetch_data` 仅做了字符串友好化（`Max retries`→"限流"），但未结构化区分限流 / 无数据 / 网络 / 不支持 | **P1** |
| S4 | **取数过程无进度，限流时无预期** | 同步取数，期间无反馈；被限流后不知道还要等多久           | `fetch_data` 同步一次性输出，`running` 仅显示"获取中…"                              | **P1** |
| S5 | **无请求间隔 / 并发控制旋钮** | 高级用户无法根据网络或数据源状态主动降速              | 无可配置项，限流阈值硬编码在未知处                                                     | **P2** |
| S6 | **数据源单一、无降级**      | 东方财富限流即全败，无备用源兜底                  | `fetch_bars` 分钟线仅走 `stock_zh_a_hist_min_em` 一条路                       | **P2** |
| S7 | **重复拉取已缓存数据**      | 已取过的区间再次取数仍全量请求，加剧限流              | 未做"本地已覆盖区间跳过"（与既有《自动加载历史数据感知与断点续传》PRD 关联，本次只做取数侧收敛）                   | **P2** |

## 2. 目标与非目标

### 2.1 目标

- **接入已有限流基础设施**：所有 akshare 取数请求在发起前经 `RateLimiter` 节流，从根上消除"请求突发→被限流"。
- **限流自愈**：识别到 429 / 限流时，自动拉长退避并下调速率，任务可自愈而非越重试越糟。
- **失败可诊断**：把失败结构化为"限流 / 无数据 / 网络错误 / 不支持"四类，用户一眼判断该重试还是换标的。
- **进度可见**：取数过程实时汇总「成功 / 失败 / 跳过 / 限流」计数，被限流时给出预计等待时长与建议。
- **可降速、可降级**：提供请求间隔/并发旋钮；东方财富限流时尝试备用数据源兜底。

### 2.2 非目标（本次不做）

- 不重构为后端异步任务队列（当前 ≤20 标的同步取数可接受，见 `fetch_data` 注释）。
- 不引入全新数据源账号体系（降级仅用 akshare 内置的备用接口）。
- 不做"增量/断点续传"的完整存储层改造（仅做取数侧"跳过已全覆盖区间"的轻量收敛，重活交给既有断点续传 PRD）。
- 不改动「已缓存数据 / 自动加载」Tab 的结构。

## 3. 用户角色

- **量化研究员**：批量取分钟线做回测，最怕"取一半被限流、成败参半"。
- **策略开发者**：已有代码清单，希望一次拉全且知道哪些失败了、为什么。
- **新手用户**：被限流时不知道怎么办，需要明确的可执行建议（"稍后重试 / 减少标的数"）。

---

## 4. 设计原则

1. **基础设施优先复用**：`RateLimiter` / `retry_with_backoff` 已存在，先接上，不另造轮子。
2. **限流即信号**：限流不是"错误终点"，而是"降速信号"——触发退避 + 限速下调，任务继续。
3. **失败不阻断**：单标的失败计入失败列表并继续，整体任务不因个别标的中断（沿用现有 `results/errors/skipped` 模式）。
4. **诊断优先于掩盖**：错误信息结构化分类，宁可向用户说清"被限流了"，也不含糊报"无数据"。
5. **最小侵入**：改动集中在服务层 `fetch_bars` / `_retry_fetch` 与回调 `fetch_data`，不动布局、不动服务层接口签名（如 `fetch_bars` 参数不变）。

## 5. 优化后的取数容错流程（分钟线为例）

```
fetch_data（串行循环，逐标的）
  └─ svc.fetch_bars([symbol], ...)
       └─ acquire_limited()              ←【新增】先向 RateLimiter 取令牌（节流，防突发）
            └─ _retry_fetch_v2(...)       ←【改造】识别限流/429：
                 ├─ 命中 → 指数退避 + 通知 limiter 降速（自愈）
                 ├─ 无数据 → 标记 "no_data"
                 ├─ 网络错 → 标记 "network"
                 └─ 港股分钟线 → 标记 "unsupported"
```

异常分类在 `fetch_bars` 返回结构里沉淀，`fetch_data` 据此渲染彩色诊断文案与汇总。

## 6. 功能需求（FR，EARS 原则）

### FR-1 取数请求统一节流（对应 S1，P0）

- **系统应（Ubiquitous）**：在每次调用 akshare 取数接口（`ak.stock_zh_a_hist*` / `stock_hk_daily` / `stock_financial_abstract` 等）前，先调用 `get_global_limiter().acquire()` 获取令牌，未拿到令牌前阻塞等待。
- **验收**：
  - `_retry_fetch`（或新封装）在发起请求前调用限流器 `acquire()`。
  - 实测连续取 20 个分钟线标的时，请求间隔 ≥ 令牌桶允许的最小间隔（默认 20 次/分钟 ⇒ 平均间隔 3s），不再突发。
  - 既有单测 `test_data_center_service` 中 `fetch_bars` 行为不变（限流器在测试环境可置为不阻塞或 mock）。

### FR-2 限流感知与自适应降速（对应 S2，P0）

- **当（Event-driven）** 某次取数抛出的异常包含限流特征（`Max retries exceed` / `HTTPSConnectionPool` / `429` / `Too Many Requests` / 东方财富 `freq` 相关文案）：
  - **系统应**将该次重试退避延长至指数序列高位（如 `base * 2^attempt + 抖动`），并调用限流器的降速接口（如临时下调 `max_per_minute` 或追加冷却时间）。
  - **系统应**在全部标的取完后，于汇总中明确标注"本次发生限流，已自动降速"。
- **验收**：
  - 模拟限流异常注入时，`fetch_data` 汇总含"限流"字样，且后续请求间隔明显变大。
  - 限流器提供降速 API（在 `rate_limiter.py` 新增 `cool_down(seconds)` 或 `set_rate(n)`），被限流路径调用。

### FR-3 失败原因结构化分类（对应 S3，P1）

- **系统应（Ubiquitous）**：`fetch_bars` 返回的每个标的结果增加 `reason` 字段，取值 `{"ok","rate_limited","no_data","network","unsupported"}`；`fetch_data` 据此渲染：
  - `rate_limited` → `✗ {symbol}: 数据源限流，已自动降速，建议稍后重试或减少标的数`（红色）
  - `no_data` → `✗ {symbol}: 该区间无数据`（灰色）
  - `network` → `✗ {symbol}: 网络异常，请检查连接后重试`（橙色）
  - `unsupported` → `⊘ {symbol}: 分钟线仅支持 A 股，已跳过`（蓝色）
- **验收**：注入四类异常，UI 分别显示对应文案与配色；不再出现"无数据"掩盖"限流"的情况。

### FR-4 取数进度与分类汇总（对应 S4，P1）— 落地为「分类汇总」（非实时流式）

- **评审结论（D8）**：`fetch_data` 为**同步回调**（`background` 生成器会与 DuckDB 锁冲突，既有注释已说明），无法在单次回调内"实时刷新"中间进度而不引入后台任务队列（属非目标）。按既有《数据中心取数体验优化》Q2 决策，本版**不实现实时流式进度**，改为：任务结束时输出**分类汇总**「成功 X / 失败 Y / 跳过 Z / 限流 W」+ 限流时给出"已自动降速，建议稍后重试或减少标的数"的可读提示。
- **系统应（Ubiquitous）**：`fetch_data` 在循环结束后，于结果区顶部输出分类计数行；`rate_limited` 单列统计（区别于普通失败）。
- **验收**：取 10+ 标的时，结果区顶部出现「成功/失败/跳过/限流」分类计数；限流场景下列出限流项并给出建议。

### FR-5 请求间隔 / 并发控制旋钮（对应 S5，P2）

- **Where（Optional）** 用户在「获取数据」卡内开启"保守模式"或调整请求间隔：
  - **系统应**读取该设置作为 `RateLimiter` 的速率参数（默认 20 次/分；保守模式降至 10 次/分；或暴露"请求间隔(秒)"滑块）。
- **验收**：勾选"保守模式"后，取数明显变慢但不再被限流；设置可被 `dcc.Store` 持久化。

### FR-6 数据源降级兜底（对应 S6，P2）— ⚠️ 评审后**暂缓 / 待定**

- **评审结论（D6）**：经核实 akshare 全部接口，A 股**全历史区间**分钟线唯一可靠源是 `stock_zh_a_hist_min_em`（东方财富）。所谓"备用源" `stock_zh_a_minute`（新浪）经实测**仅返回当日 / 最近一个交易日的分钟数据**，不支持任意历史区间回填，无法作为限流降级替身；腾讯 / 其他源在 akshare 中亦无等价的全历史分钟接口。因此"切换备用数据源"在当前技术栈下**不可靠**，本版**暂缓实现**，限流主缓解手段改为依赖 FR-2 自适应降速 + FR-5 保守模式。
- **后续可选方向（非本版）**：① 引入非 akshare 的行情供应商（券商 PB / 付费 API）作为真降级源；② 仅对"当日补数"场景用 `stock_zh_a_minute` 做日内兜底（范围受限，仅当请求区间落在当日时）。
- **验收（本版）**：不新增降级开关 UI（避免死模块，呼应既有原则）；限流时在结果中明确提示"数据源限流，已自动降速，建议稍后重试或减少标的数"，由 FR-2 承接。

### FR-7 已覆盖区间跳过（对应 S7，P2，轻量收敛）— ✅ 评审确认可实现

- **评审结论（D7）**：`CacheCatalogService.record_coverage` 在写分钟线时已持久化 `minute_start` / `minute_end` 区间边界与 `minute_periods` 周期集合（`get_coverage_for_tickers` 可批量读取）。故"目标区间是否已被完全覆盖"可被精确判断，**本功能可行且低风险**。
- **系统应（Ubiquitous）**：`fetch_bars` 在循环前**批量**查一次 `catalog` 覆盖度（`get_coverage_for_tickers(symbols)`）；对于每个标的，若 `has_minute` 且请求 `period` 已含于 `minute_periods`，且 `[start, end]` 被 `[minute_start, minute_end]` **完全包含**，则跳过该标的并记 `skipped`（原因"已缓存"），不发起请求。
- **边界**：仅当请求区间被已缓存区间**完全覆盖**才跳过；部分重叠（如延伸了结束日）仍发起请求（增量补齐，不做区间裁剪），避免返回陈旧切片。
- **验收**：对已全覆盖标的再次取数，不发起网络请求，结果标记"已缓存跳过"，总请求数下降。

## 7. 关键交互与用户旅程

**批量分钟线（正常）**：勾选 20 个 A 股 → 设近 7 天 → 点获取 → 请求经限流器匀速发出 → 全部成功 → 汇总"成功 20"。

**批量分钟线（限流）**：勾选 20 个 → 第 8 个被限流 → 系统自动降速、退避后继续 → 最终"成功 17，限流 3" → 限流项红色提示"建议稍后重试或减少标的数" → 点「去行情看板」查看已成功的 17 个。

**保守模式**：资深用户勾"保守模式" → 速率 10/min → 全程不被限流但更慢。

**降级兜底**：开启"数据源降级" → 东方财富限流项改走新浪源 → 部分标的"降级源"成功。

## 9. 产品决策与开放问题

1. **限流基础设施已存在，本次核心是"接上"而非"新建"**：`RateLimiter` 与 `retry_with_backoff` 都已写好，未接线是本次根因。决策：**复用**，在 `_retry_fetch` 内统一接入，不新增限流类。
2. **限流降速的"下限"**：降速不能无限降（如降到 1 次/分会让 20 标的数分钟）。建议下限 5 次/分，并配"保守模式"显式更慢。待研发确认退避上限与冷却时长。
3. **失败分类的文案口径**：`rate_limited` 与 `network` 在用户看来都"暂时不可用"，但建议区分（限流可稍后重试、网络需查连接）。沿用现有红色/橙色配色。
4. **降级源（FR-6）评审后暂缓**：核实 akshare 后，A 股全历史分钟线仅东方财富 `stock_zh_a_hist_min_em1` 可靠，新浪 `stock_zh_a_minute` 仅支持当日，无法做历史区间降级。故本版**不实现**切换备用源，限流主缓解靠 FR-2 自适应降速 + FR-5 保守模式；降级开关 UI 不新增（避免死模块，呼应既有原则）。待引入第三方供应商再评估。
5. **FR-7 已覆盖跳过确认可行**：`record_coverage` 已持久化 `minute_start/minute_end` 与 `minute_periods`，`get_coverage_for_tickers` 可批量读取，实现成本低、风险小，本版纳入实现（D7）。
6. **FR-4 进度落地为分类汇总**：同步回调模型下无法实时流式刷新（D8），沿用既有 Q2 决策，不做后台队列；以"结束时的分类计数"替代实时进度。
7. **FR-7 跳过阈值**：采用"请求区间被已缓存区间完全包含"作为跳过判据（非时间阈值），规避"未过期"定义的歧义，逻辑更稳。

## 11. 边界与异常

- 限流器在单测中必须可禁用/ mock，否则测试变慢且不稳定（FR-1 验收已注明）。
- 限流降速有下限（建议 5 次/分），避免任务无限拖长。
- 备用源失败不计二次限流惩罚，避免雪崩。
- 网络异常与限流区分：网络错不触发降速（降速对网络错无效），仅提示查连接。
- 降级取得的数据标注来源，用户可识别。
- 取数进行中按钮禁用（`running`）与空池禁用（既有 FR-5）互不冲突，本次不改。

## 13. 影响面与风险

- **正向**：从根上消除"批量分钟线必被限流"，取数成功率与体验大幅提升；复用已有基础设施，改动面小。
- **风险**：
  - 限流器接入位置若只在 `_retry_fetch`，需确保所有分支都走它（当前 daily/minute/financials/adj 四个分支均调 `_retry_fetch`，统一改一处即可）。
  - 限流降速阈值需压测确定（避免过松仍限流、过紧太慢）。
  - 降级源字段口径差异需在「已缓存数据」可识别。
- **回归**：仅「数据查询」取数链路与服务层 `fetch_bars`；行情看板读取的是已落库数据，不直接受影响。

### 15.4 评审结论与必改项

- **方向 ✅**：根因明确（限流器未接线），复用现成设施，改动小收益大。
- **进入研发前必须完成**：① `_retry_fetch` 接入 `acquire()`（D1）；② 限流特征识别 + `cool_down`（D2）；③ 统一 limiter 实例（D3，用全局单例）；④ 测试可禁用限流器（D5）；⑤ 失败 `reason` 分类与配色规范（DES-3）；⑥ FR-7 覆盖度跳过（D6，需补 `get_coverage_for_tickers` 字段）；⑦ FR-4 落地为分类汇总而非实时流式（D7）。
- **本版不做（评审决议）**：FR-6 备用源降级——技术栈不可靠，暂缓（D4）。
- **风险等级：低-中**。改动集中在 `fetch_bars`/`_retry_fetch` 单点、`fetch_data` 渲染，及「获取数据」卡新增 1 个"保守模式"开关；不触 `fetch_bars` 接口签名与行情看板/缓存 Tab。
