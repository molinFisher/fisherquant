# PRD：量化系统能力补齐（对照《量化交易系统必备功能清单》）

- **文档版本**：V1.0
- **作者视角**：高级产品经理
- **日期**：2026-07-29
- **对照基线**：`gemini-code-1785336991006.md`《量化交易系统必备功能清单（完整版）》
- **系统基线**：FisherQuant（研究 / 回测 / 模拟交易 平台）

---

## 1. 背景与评估方法

用户提供了一份"量化交易系统必备功能清单"，覆盖**数据行情层、策略研发与回测层、风险控制层（事前/事中/事后）**三大块。本 PRD 以此为基准，对 FisherQuant 当前代码做逐条能力映射（源码审计 + 关键代码点验证），识别出**已实现 / 部分实现 / 骨架占位 / 缺失**四类状态，并据此形成补齐方案。

评估结论先行：**FisherQuant 已具备"研究—回测—模拟交易"主链路的实质实现**（事件驱动回测、T+1、涨跌停锁死、滑点/费用、基础事前风控、Brinson 行业归因、因子库），但**实盘交易闭环与若干研究质量/安全关键能力整体缺失或薄弱**。其中 `fisher/broker/live.py` 全部为 `NotImplementedError` 占位，意味着一切"依赖真实柜台"的能力（实时行情接入、实盘下单、实时风控接管、对账）当前**无法成立**。

> 因此本 PRD 采用**范围分级**策略：把"研究/回测平台自身可闭环补齐"的能力列为 **In-scope（分期实现）**，把"必须依赖实盘券商接入"的能力列为 **Out-of-scope 战略项（需先立 broker 集成专项）**，避免一份 PRD 既写研究增强又写生产交易基建而失去落地性。

## 3. 缺失 / 薄弱功能清单（对照表 + 优先级）

优先级定义：**P0** = 影响回测结论可信度或交易安全，必须补齐；**P1** = 高价值研究/风控增强；**P2** = 增强项。

### 3.1 数据行情层
| 清单项 | 状态 | 缺什么 | 优先级 |
|---|---|---|---|
| 多协议实时接入(WS/TCP/FIX/UDP) | 缺/骨 | 仅 akshare REST；无动态订阅/多源融合/时间戳对齐 | P2(依赖 broker 专项) |
| 行情清洗：统一模型(Tick/OrderBook/Transaction) | 缺 | 仅 Bar/Quote/Snapshot | P1 |
| 异常过滤(越界/量倒挂/时间倒流/停牌标记) | 缺 | 无脏数据检测 | P1 |
| 插针补缺 / K线合成引擎(1s/1h/Vol/Dollar/Tick Bar) | 缺 | 仅现成日/分钟 | P1 |
| 盘口深度重建(L3→L2) | 缺 | 无 OrderBook 重建 | P2(依赖实时行情) |
| VWAP / OBI / 截面因子 | 缺 | 时序因子有，截面/VWAP/OBI 无 | P1 |
| 动态复权 / 期货换月 / 连续合约 | 部分 | 股票复权有，期货换月无 | P1 |

### 3.2 策略研发与回测层
| 清单项 | 状态 | 缺什么 | 优先级 |
|---|---|---|---|
| 策略生命周期 on_tick/on_order/on_trade/on_stop | 部分 | 有 on_init/on_bar/on_signal/on_order_filled/on_risk_close | P1 |
| 市价单撮合 | 缺 | `order_type` 恒为 limit，无市价单 | **P0** |
| 撤单延迟/失败率、排队位置、冲击成本模型 | 缺 | 仅多成交价+滑点 | **P0** |
| 向量化回测模式 | 缺 | 仅事件驱动 | P2 |
| 停牌/可交易状态校验接入回测 | 缺 | `SuspensionEvent` 已定义但**回测未使用** | **P0** |
| 生存者偏差防护 | 缺 | 退市标的未纳入 | **P0** |
| 多因子 Style 归因(Size/Value/Momentum) | 缺 | 仅 Brinson 行业 | P1 |
| 卡玛比率 / 年化波动率 | 缺 | 指标表不完整 | P1 |

### 3.3 风险控制层
| 清单项 | 状态 | 缺什么 | 优先级 |
|---|---|---|---|
| 单笔量/名义金额上限 | 缺 | pre_trade 无 | **P0** |
| 总仓位/杠杆/挂单上限 | 缺 | pre_trade 无 | **P0** |
| 频率限制(事前) | 缺 | 无报单/撤单频率约束 | P1 |
| 实时回撤熔断 | 部分 | `risk/realtime.py` 有 VaR/β/回撤熔断 | 已具备(模拟) |
| 动态止损/止盈 | 部分 | `paper/engine.py` 条件单已实现 | 已具备(模拟) |
| 异常监控(延迟/中断/连续拒单接管) | 缺 | 仅当实时链路存在时才有意义 | P1(依赖实时) |
| 对账校验(本地 vs 柜台) | 缺 | broker/live 占位 | **P0**(沙盒内可做) |
| 合规日志留痕 | 缺 | 无结构化审计日志 | **P0** |

## 4. 范围决策

### In-scope（本平台可闭环补齐，分期实现）
- **P0 研究安全底座**：市价单撮合、撤单延迟/失败率/排队/冲击、停牌校验接入回测、生存者偏差防护、单笔/名义/总仓位/杠杆/挂单上限、沙盒内对账、合规日志。
- **P1 研究增强**：K线合成引擎、异常过滤+插针补缺、截面/VWAP/OBI 因子、动态复权/期货换月提示、完整生命周期回调、多因子 Style 归因、卡玛/年化波动、事前频率限制。

### Out-of-scope 战略项（需先立"broker 集成专项"）
> 以下能力**依赖真实柜台/实时行情源**，在 `broker/live.py` 落地前无法成立，故不在本 PRD 实现范围，仅作为依赖项记录：
- 多协议实时行情接入、动态订阅、多源融合灾备、时间戳对齐
- L3 逐笔→L2 盘口深度重建
- 实盘下单（FIX/UDP 组播等）、真实撤单延迟与拒单接管
- 实盘实时风控接管、真实对账
- 向量化回测（评估为 P2，可独立小迭代）

## 5. PRD 主体（需求组）

### 需求组 G1 — 回测撮合仿真补全（P0）
- **目标**：让回测成交更接近真实，消除"看似盈利实则不可成交"的假信号。
- **用户故事**：研究员希望回测能模拟市价单、排队、撤单失败与冲击成本，否则策略上线即失真。
- **功能要求**
  1. 新增 `order_type ∈ {limit, market}`；市价单按下一根 Bar 开盘价/对手价撮合。
  2. 限价单引入**排队位置模型**（按挂单量与盘口量的相对位置估计成交概率/时间）。
  3. 新增**撤单延迟**（指令到柜台的网络延迟）与**撤单失败率**参数。
  4. 新增**市场冲击成本模型**（基于成交量与盘口深度的冲击成本，替换/增强现有固定滑点）。
  5. **实现约束（MVP 与校准）**：排队位置与冲击成本属**校准型模型**，平台当前**无真实成交样本用于标定**，全量启用可能引入新的系统性偏差。本期定义最小可用版本（MVP）：先实现**市价单撮合**（按次根 Bar 开盘价/对手价）与**撤单延迟/失败率**（参数化、默认关闭）；排队位置与冲击成本作为可选进阶模块，提供可关闭的简化模型，并在 UI 明确标注"近似、待校准"。
- **验收标准**
  - AC-G1.1：同一策略同数据下，开启冲击模型后成交均价相对基准（仅滑点）偏离须在定义阈值内（如 ±X%，X 待标定）；并以 golden snapshot 固化"默认参数"回测结果，CI 中比对确保 0 漂移。
  - AC-G1.2：市价单在回测中能被撮合且 `order_type` 正确留痕于成交记录。
  - AC-G1.3：排队位置/撤单失败率参数变化能被引擎读取并影响成交序列。
- **三视角要点**
  - 开发：在 `backtest/fill.py` 与 `engine.py` 扩展，保持现有事件驱动接口；新增参数一律**默认关闭**（feature flag 隔离），避免旧回测用例漂移。序列化层以 `metadata.get()` 容缺（已确认），新增回测字段（order_type/queue/impact）向后兼容，但须补"历史回测记录加载"回归测试确认旧文件可正常载入。
  - 设计：参数集中在"回测设置"面板，分组为"成本/滑点"与"撮合仿真"，附 tooltip 说明对结果的潜在影响。
  - 测试：单测覆盖市价单、排队位置概率、撤单失败路径；回归既有 limit 用例（默认参数结果不变）。

### 需求组 G2 — 可交易状态与生存者偏差防护（P0）
- **目标**：回测自动剔除停牌、涨跌停锁死等不可交易时段信号，并保留退市标的历史。
- **功能要求**
  1. 将 `event/types.py` 已定义的 `SuspensionEvent` 接入回测引擎：标的处于停牌/临时停牌时，信号被抑制并标记。
  2. 涨跌停锁死（无法买入/卖出）沿用现有约束并补充"当日首笔即锁死"边界。
  3. 数据目录增加"包含退市/下架标的"开关，默认开启，供生存者偏差防护。
- **【数据依赖 · 必须先行】**：系统当前**无任何停牌状态接入**（`fisher/market/`、`fisher/store/` 均无相关字段），亦**无退市标的/标的宇宙概念**（全仓检索无 `suspension/停牌/退市/delisted` 相关实现）。实现前须先补齐数据基础，否则 `SuspensionEvent` 无输入、退市开关无可切换数据：
  1. 停牌状态数据源：接入 akshare 停牌/复牌接口，落库至缓存目录（新增 `suspensions` 表或并入 `cache_catalog` 状态位）。
  2. 退市标的来源：接入 akshare 退市/终止上市列表，构建"含退市标的的标的宇宙"，供开关引用。
  3. 缺数据降级：数据源不可用时，G2 功能自动禁用并提示，不影响回测主流程。
- **验收标准**
  - AC-G2.1：含停牌区间的标的，回测在停牌期不产生成交，并在报告标注"因停牌跳过 N 次信号"。
  - AC-G2.2：退市标的在历史区间可被回测引用（开关开启时）。
- **三视角要点**
  - 开发：复用 `SuspensionEvent`；但**须先完成上述数据依赖**（停牌表 + 退市标的宇宙），在引擎时间推进中读取标的状态。退市开关映射到新建的标的宇宙配置。
  - 设计：回测结果"信号有效性"区新增"被跳过"计数（与策略中心就绪列视觉一致）。
  - 测试：构造停牌/退市 fixture，断言不成交与可引用。

### 需求组 G3 — 事前风控补全（P0）
- **目标**：为模拟交易补齐单笔/名义/总仓位/杠杆/挂单上限，防止乌龙指与超额暴露。
- **功能要求**
  1. `risk/pre_trade.py` 扩展规则：单笔最大量、单笔最大名义金额、单标的持仓上限、总杠杆上限、未成交挂单上限。
  2. 规则可在"设置—风控"面板配置，作用于模拟交易与（未来）实盘。
- **验收标准**
  - AC-G3.1：超出单笔名义金额的下单被拦截并返回明确原因。
  - AC-G3.2：总持仓逼近杠杆上限时新开仓被拒。
- **三视角要点**
  - 开发：规则以策略模式叠加，复用现有 `PreTradeChecker` 入口。
  - 设计：风控设置分组清晰，越界时前端红字提示。
  - 测试：参数化单测覆盖每条规则的触发边界。

### 需求组 G4 — 沙盒对账与合规日志（P0）
- **目标**：即便无真实柜台，模拟交易也需可审计、可对账，为未来实盘对账铺路。
- **功能要求**
  1. 模拟交易每日生成"本地持仓/资金快照"，与成交流水做内部对账（差额告警）。
  2. 全链路合规日志：下单、撤单、成交、风控拦截均结构化留痕（时间/标的/数量/原因/结果）。
- **验收标准**
  - AC-G4.1：对账不一致时产生告警日志且可定位差异来源。
  - AC-G4.2：任一成交/拦截事件均能在审计日志检索到。
- **三视角要点**
  - 开发：日志走统一 `logging` 模块，结构化为 JSON。对账**不在** `paper/engine.py` 的"清算钩子"——该文件当前仅有 `submit_order/cancel_order/get_*/check_conditions/on_bar/_apply_fill`，**无清算/对账钩子**（已核实）。应在模拟交易主循环或 `scheduler` 中新增 `daily_settle()` 日终步骤触发对账（本地持仓/资金快照 vs 成交流水），对账对象明确为"成交流水 ↔ 持仓/资金快照"。
  - 设计：新增"审计日志"查看入口（可分页/筛选）。
  - 测试：构造故意不一致场景，断言告警；断言日志字段完整。

### 需求组 G5 — K线合成与数据清洗（P1）
- **目标**：支持自合成多周期 K 线与基础脏数据防护，提升研究灵活性。
- **功能要求**
  1. K线合成引擎：基于 Tick/分钟 Bar 合成 1s/1h/VolBar/DollarBar/TickBar。
  2. 异常过滤：价格越界、成交量倒挂、时间戳倒流检测与标记。
  3. 插针补缺：断点处向后追溯补齐。
- **验收标准**
  - AC-G5.1：给定分钟序列，合成 1h/VolBar 结果与手算一致。
  - AC-G5.2：人工注入脏数据可被识别并标记不入库。
- **三视角要点**
  - 开发：合成器纯函数化便于单测；清洗在 `store/repository` 写入前校验。
  - 设计：数据中心的"获取"流程增加"清洗预览"步骤。
  - 测试：合成器边界 + 脏数据样例。

### 需求组 G6 — 因子与绩效深化（P1）
- **功能要求**
  1. 新增截面因子与 VWAP、OBI；提示期货换月/连续合约拼接需求。
  2. 绩效补全：卡玛比率、年化波动率；新增多因子 Style 归因（Size/Value/Momentum 暴露与 Alpha/Beta 拆解）。
- **验收标准**
  - AC-G6.1：Style 归因输出各因子暴露度与贡献，可被报告中心渲染。
  - AC-G6.2：卡玛/年化波动计算与第三方核对一致。
- **三视角要点**
  - 开发：归因接入 `analytics/attribution.py`；因子接入 `factor/`。
  - 设计：报告中心新增"因子暴露"图。
  - 测试：小市值/价值组合断言暴露符号正确。

### 需求组 G7 — 策略生命周期与频率限制（P1）
- **功能要求**
  1. 策略框架补齐 `on_tick/on_order/on_trade/on_stop` 回调（如有线回调则串联）。
  2. 事前频率限制：单位时间最大报单/撤单频率。
- **验收标准**
  - AC-G7.1：回调在对应事件触发；AC-G7.2：超频下单被限流。

## 6. 依赖与风险

- **阻塞依赖（最高优先级）**：`broker/live.py` 为占位实现。凡"实时行情/实盘下单/实盘风控接管/真实对账"均依赖"broker 集成专项"先行立项（Out-of-scope）。
- **风险 R1**：强化撮合仿真若默认开启，将导致历史回测数值漂移，旧用例/报告不可比 → 对策：默认关闭，显式开关。
- **风险 R2**：生存者偏差防护需退市标的历史数据可得性 → 对策：开关默认开，缺数据时降级并提示。
- **风险 R3**：Style 归因需因子暴露基准（如风格指数）→ 对策：先接内部代理基准，标注近似性。
- **风险 R4（评审补充）**：G1 排队/冲击模型属校准型，无真实成交样本 → 对策：MVP 仅市价单+撤单延迟/失败率（默认关）；进阶模型标注"近似、待校准"，不宣称精度。
- **风险 R5（评审补充）**：G4 审计日志在高频模拟下体量无限增长 → 对策：定义留存策略（按策略分库/保留 N 天）与查看端分页+检索性能预算（如 10w 行内 < 1s）。
- **已确认安全项（评审）**：回测序列化层使用 `metadata.get()` 容缺，新增字段向后兼容，旧回测记录可正常载入（仍需补加载回归测试）。
